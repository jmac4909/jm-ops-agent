# Investigating an incident after recovery

An investigation can start after another team fixes an incident, even if this agent collected nothing while it was failing. Describe it in the same launch form used for current issues, for example `entry-api returned errors in TEST yesterday; another team restored service`. The agent infers an incident window from dates or timestamps, or searches earlier retained TAS failures when recent searches do not establish a failure. No separate mode or previous investigation record is required. See [Adaptive investigations](adaptive-investigations.md) for discovery bounds and ambiguity handling.

Results and status JSON retain the resolved `incidentStart` and `incidentEnd` in UTC. Dates have no age cap. Explicit search periods can span up to one year. Calendar clues such as `last month`, `three months ago`, and `in May 2025` resolve to UTC periods; periods wider than seven days sample retained errors and narrow to an observed failure when available. The original requested period remains evidence, and the selected failure is explicitly a sample, not coverage of every incident. Invalid, future and reversed dates require clarification before collection.

| Evidence | Historical behavior |
| --- | --- |
| TAS application logs | Splunk error searches use the incident window and retain up to five samples per collection to reserve history/dependency capacity. Additional service-log and business-call requests retain that window. Plain text goes through the existing normalization and sanitizer. |
| Tracking IDs | Search the supplied window; no automatic expansion into present-day traffic. Gateway/CF source coverage still depends on connector configuration. |
| Dependencies | Resolve registered relationships and observed registered destinations. Use each service's own failure time when choosing its Jenkins candidate. Registry mappings are current and may differ from those at incident time. |
| Jenkins | Seek indexed build timestamps near the service-specific failure anchor, then read at most 100 nearby retained build details. The seek uses at most 40 metadata requests within a shared 20-second bound, with no console/stage fan-out. It can pass thousands of newer builds without reading all their details; ordering, deletion and scan bounds can still leave gaps. One timeline item retains a pre-window candidate, the latest successful build completed by the first observed service failure, and up to six representative incident/recovery builds. Missing completion times cannot select a historical candidate. |
| Source history | Search up to 100 branch commits and retain up to ten before/during the incident. Separately search possible fixes after the incident. Compare the historical Jenkins candidate with the first retained successful later candidate when available. Titles and bounded diffs are evidence, not proof of causation. |
| Config server | Find the registered config file's latest commit at or before incident start, then read the file at that commit SHA. Record the revision and timestamp, redact secrets, and label runtime values unverified. No fallback to current branch content. |
| CF events | Read the retained listing. The CLI does not filter by incident time; the evidence explicitly distinguishes collection time from timestamps inside the event listing and labels coverage unverified. |
| Current snapshots and probes | Current runtime health/configuration, recent CLI logs, and direct API/database probes cannot reconstruct historical conditions and are excluded from retrospective collection. |
| Kubernetes logs | Historical application-log coverage is currently unavailable: the Splunk application templates use CF fields, and current pod logs are not an archive. Other registered repository/Jenkins evidence can still be collected, with this gap stated. |

The recovery comparison ends 72 hours after incident end, capped at the time the evidence scope was resolved. Incident log bounds are start-inclusive and end-exclusive; records at incident end belong to the possible recovery period. This cutoff remains fixed when the investigation is reopened later; an explicit correction establishes a new scope and cutoff. GitLab's inclusive API bounds may return an exact-boundary commit in both advisory samples; commit IDs and dates remain explicit.

Follow-ups use the stored window unless the user supplies corrected timing. An explicit current question such as `why is this failing now?` returns to current collection; `why was this broken in May 2025?` searches that old month. Each user turn receives a new bounded collection allowance shared across its reasoning and traffic reads; cumulative audit counts are retained. A correction labels earlier evidence as belonging to the previous window, removes it from active reasoning, and starts fresh model context. Source inspection runs automatically when reasoning requests it, using historical Jenkins candidates with their uncertainty stated. Persisted candidates and dependency scope are reused after reload, so losing the build from Jenkins' retained history does not force inspection of today's fixed revision.

Recovery does not erase retained log and repository evidence, but the agent cannot recover expired logs, deleted Git history, historical DynamoDB contents, or a missing deployment attestation. A platform restage can invalidate a Jenkins-to-runtime revision assumption. A later successful build does not prove the fix. When no concrete historical failure is established, the result remains UNKNOWN even if present-day systems are healthy or repository text suggests a cause. If Claude is unavailable, retrospective analysis also completes as inconclusive instead of inferring a cause from repository keywords.

Local regression tests cover a new investigation after recovery, a good/bad/fixed deployment sequence, dependency traversal, per-service failure anchors, missing retention, false failure markers, follow-up/code reloads, historical config wire requests, bounded Jenkins history, input validation, and the rendered HTTP form/status flow. They use fictional fixtures and mocked reasoning; they do not validate enterprise retention, credentials, or Claude's diagnosis of a real incident.
